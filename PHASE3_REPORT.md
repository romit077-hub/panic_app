## Room architecture

PanicApplication owns one lazily created file-backed PanicDatabase named panic.db.
Database version is 1. It has one tasks table and an index on completion/deadline.
There is no destructive migration fallback, launch-time seeding, or main-thread query option.
The priority converter stores stable enum names as TEXT.

TaskEntity fields:

| Field | Type |
| --- | --- |
| id | Long, autogenerated primary key |
| title | String |
| description | String |
| subject | String |
| dueDateMillis | Long, epoch milliseconds |
| estimatedMinutes | Int |
| priority | TaskPriority: LOW/MEDIUM/HIGH |
| isCompleted | Boolean |
| createdAt | Long, epoch milliseconds |

TaskDao supports observing all/pending/completed tasks, getting by ID, insertion,
editable-field updates, deletion, setting completion, and an atomic completion toggle.
Pending tasks sort by dueDateMillis and ID. Updating a form changes only editable
columns, preserving completion and createdAt even when an older form is saved.
Updates and deletes report affected rows; missing records produce a visible error.

TaskRepository is a simple concrete DAO wrapper. It validates input at the write
boundary, trims text, and exposes Flow queries. Composables never call the DAO.
No use-case hierarchy, mutable fake repository, or independent stored task list exists.

## ViewModels and state

TasksViewModel exposes StateFlow<TasksUiState>: loading, observed tasks, load errors,
action errors, and busy task IDs. It uses viewModelScope and a retryable Room observer.
Both Dashboard and Tasks read the same observed state. No optimistic list mutations
are used; Room emissions drive saved-task changes.

TaskEditorViewModel handles one add/edit destination. It loads an existing task,
stores unsaved primitive draft fields in SavedStateHandle, validates fields, prevents
concurrent saves, and signals navigation only after a successful database write.
A missing task is shown as an error, never silently converted to a new task.
ViewModels have no Android Context. Dependency factories remain in the UI composition root.
Cancellation is rethrown; expected database/storage failures are logged and shown with
retry/dismiss actions. Unknown exceptions are not silently swallowed.

## Form and task actions

One shared form supports title, description, subject, date, time, estimated minutes,
and priority. It uses stable native date/time dialogs with lifecycle cleanup.
Required title/subject cannot be blank. Text lengths and duration (1–10,080 minutes)
are bounded. Deadlines accept years 1970–2100; past deadlines are deliberately allowed
to track overdue work. Formatting happens only at display time.

Local date/time selection converts to epoch timestamps in the device zone. Nonexistent
DST times are rejected; repeated DST times choose the earlier offset. This selection
policy is covered by source tests. Draft state survives navigation configuration
recreation. Save/Cancel/Back controls prevent leaving midway through an active write.

Tasks has loading, error, empty, content, and filtered-empty states. Pending, Completed,
and All filters use the existing chip design. Completed tasks remain in Room, have a
struck-through title, and can be restored. Delete opens an explicit confirmation dialog.
Card taps never delete. Action controls are disabled while their task is being updated.

Dashboard uses real pending/completed counts and the earliest pending timestamp
(including overdue work). It shows an empty/caught-up state and a real Add Task action.
No random scores or critical counts are applied to saved tasks.

Calendar, PANIC, and Analytics remain clearly labelled design previews using sample
data, separate from saved tasks. No analytics engine, risk algorithm, alarms,
notifications, WorkManager, network permission, authentication, or cloud service added.
Settings reflects that tasks now use Room; preference switches are still temporary.

## Manual acceptance after a successful build

- First launch: no saved tasks and a clear empty state.
- Add a task, check Dashboard counts, Tasks fields, and deadline display.
- Edit all fields and verify the same task ID remains; creation time is preserved.
- Complete a task; inspect Completed/All; restore it to pending.
- Cancel deletion, then confirm deletion for a disposable task.
- Force-stop and relaunch: saved tasks persist without duplicate sample insertion.
- Rotate an unsaved form: entered values remain.
- Check invalid title/subject/duration and a past deadline.
- Check system Back, tab state, keyboard insets and dark mode on a small screen.
- Open all design-preview destinations: labels distinguish them from real saved data.

Resolve any build/runtime defects before approving Phase 4.
